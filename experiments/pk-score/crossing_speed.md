# 交差スコアの求解負荷と、目的値を保つ高速化

下側のリンク制約を削る定式化により、同じ300配列の時間を28.255→26.658秒へ5.65%短縮した。時間比の95%対応bootstrap区間は `[0.90975,0.97285]`。全予測が一致し、PK対F1は0.243064のまま。ただしスコアなしの基準よりまだ1.58倍の時間がかかる。

前回の形状＋BPPスコアの時間増加を調べ、同じ整数構造のスコアを保つ定式化を比較した。スコアの重みはγ=1、λ=0.05、初期BPP・候補cut・refinementなし・自動閾値10候補を維持し、学習し直さない。

## 遅くなる理由

前回の評価用300配列では、基準の17.875秒に対して統合スコアが29.294秒だった。PKスコアの定式化は全配列・全閾値を合計して0.110秒で、最適化時間が16.585→27.822秒へ増えていた。増加分の大半はスコア式の計算ではなく求解である。追加時間11.419秒のうち8.012秒（約70%）が20配列に集中した。

現在のスコアは、上位対xと、その交差相手の重み付き選択数rの積を評価する。

```
r = Σ wj yj
z = x r
L ≤ r ≤ U
```

整数変数x、yjの数は増えないが、zのリンク行が多数の塩基対変数を結び付ける。追加行と非ゼロ係数を持つLPを解き、その分数解に対するカットや探索を行う必要がある。変数・行の増加を線形に抑えることは、求解時間を一定倍率に抑えることとは異なる。

積の緩和には、分数解で実際の積より多くの加点が許される場合もある。例えばw=1、U=3、x=0.5、r=1なら、積は0.5だが、上側の線形制約はz=1まで許す。これは整数解の誤採点ではなく、整数解を見つける途中の緩和の性質である。

調整用282配列の診断では、基準の探索ノード数1213、LP反復数36705に対し、統合スコアの従来式は1271、62464だった。ノード数は約5%、LP反復数は約70%増加した。この標本では、探索ノード数だけでは時間増加を説明できず、LPの処理負荷が大きい。[HiGHSの診断項目](https://ergo-code.github.io/HiGHS/dev/structures/structs/HighsInfo/)を利用して記録した値であり、CPU処理を段階別に分解したプロファイルではない。

## 比較した方法

### 数値の正規化

zを各行の最大絶対重みcで割り、目的係数をcにする。行列内の交差重みが絶対値1以下になる。目的値・数学的なLP緩和は変わらず、変数・行も増えない。`--pk-crossing-normalize` で試したが、調整用282配列の三回測定では19.273→20.952秒となり、約9%遅くなった。

### 同レベル内の非交差性による上下限の強化

ある上位対を横切る下位対は、上位対の左端を横切る組と右端を横切る組に分かれる。同じ側で同時に選べる対は厳密な入れ子の鎖であり、両側を同時に選ぶには左組の最大右端が右組の最小左端より手前にある必要がある。この性質から、正の重みと負の重みの絶対値の最大和をそれぞれO(m log m)、O(m)メモリで計算し、L、Uを締める。

`--pk-crossing-tight-bounds` は追加変数・行を作らず、整数構造の許容範囲を変えない。10候補・282配列で1225行の上下限を締めたが、時間は19.273→19.207秒で、約0.3%の短縮にとどまった。正規化との併用は20.760秒だった。全設定の最終予測・各閾値の目的値は一致した。ここでの時間比較はこの調整用標本での結果であり、評価用300配列の速度確認には採用しなかった。

### 最大化に不要な下側のリンク行を削除

従来は以下の四種類の制約で積の等式を強制していた。L=0またはU=0の場合は対応する行を省く。

```
z ≤ U x
z ≥ L x
z ≥ r - U(1-x)
z ≤ r - L(1-x)
```

補助変数zは、正の目的係数で最大化され、他の目的や構造条件には使われない。したがって次の上側二種類だけでよい。

```
z ≤ U x
z ≤ r - L(1-x)
```

x=0ならzの最大値は `min(0,r-L)=0`。x=1なら `min(U,r)=r`。L≤r≤Uが成り立つ全ての整数塩基対割当について、最大化後のスコアは元と同じである。負の重みや混在にも成立する。z自身の上下限L、Uは残し、元の交差支持行・塩基対候補・整数変数は残す。

これは補助変数の任意の非最適値まで積に等しくする定式化ではない。整数構造ごとに補助変数を最大化した目的値を保つ定式化である。IPknotの目的の最大化と、zの正の係数に依存する。最小化へそのまま転用する方法ではない。

`--pk-crossing-hypograph` で有効にする。追加連続変数は同数、追加行は各支持行につき最大四行から最大二行へ減る。通常の上下限の下では、分数のx、yjを固定したときの最大zも従来と同じであり、通常のLP目的値の緩和を厳しくする方法ではない。上下限強化を併用するとLPへの追加効果は変わるため、単独と併用を分けて測った。

## 設定選択と検証

全ての比較は同じ保存済み初期BPP、HiGHS1.15.1一スレッド、Release、GCC13.3、ARM64で行った。設定順をRNA・反復ごとに巡回させた逐次実行を三回行い、RNAごとの時間中央値を合計する。BPP計算・学習の時間は含めず、デコーダの読込・モデル構築・求解・出力を含める。

初期の二案と、下側行削除の三案を、以前と同じ調整用282配列で比較した。

| 下側行削除の比較 | 時間 | 最大追加行 | 探索ノード数 | LP反復数 |
|---|---:|---:|---:|---:|
| 従来式 | 18.309秒 | 403 | 1271 | 62464 |
| 下側行削除のみ | 16.879秒 | 173 | 1235 | 63492 |
| 下側行削除＋上下限強化 | 17.061秒 | 173 | 1231 | 63449 |
| 下側行削除＋正規化 | 18.202秒 | 173 | 1233 | 64744 |

時間は三回の中央値、ノード・反復数は各RNAの一回目を合計した診断。従来式の時間は最初の二案の比較時とは別の実行であり、異なる測定段階の秒数を直接引いて速度効果としない。新しいバイナリ内の従来式を対照とし、前回のバイナリそのものも対照に含めた。

全候補で282配列の最終予測は一致した。ただし1配列 `bpRNA_RFAM_38551` の1閾値で、従来式の目的値5.6514993677に対し新式は5.65179861282となった。従来式は相対ギャップ5.29497e-5で終了し、新式は0だった。HiGHSの[既定の相対ギャップ許容値](https://ergo-code.github.io/HiGHS/dev/options/definitions/#option-mip-rel-gap)は1e-4で、従来式もこの意味で最適ステータスになっていた。

本番の停止許容値を変えず、診断用にIPラッパーの相対ギャップを0、絶対ギャップを1e-10にした別バイナリを作った。同じRNAで従来式と新式の10閾値の目的値が全て一致し、予測ファイルも一致した。相違した閾値では両方が5.65179861282になった。

当初の「全閾値の目的値の差が1e-7以下」という速度選択規則では、従来式が選ばれた。この診断を根拠に、300配列の新しい測定を始める前に「最終予測が一致し、目的値が悪化しない（差の下限−1e-7）」へ修正し、変更前の設定選択を保存した。精度の正解ラベルによる選択や、PKスコアの重み調整は行わない。固定した方式は下側行削除のみである。

評価用には前回と同じ300配列を使い、スコアの回帰と速度を測る。新しい独立の精度標本とは呼ばない。速度比の95%区間は同じRNA類似性クラスタを単位とする5000回の対応bootstrap、seed20261004。三反復を900独立RNAとは扱わない。

小規模な正負・混在・二／三レベルの整数割当を全列挙し、全ての定式化の最大値を独立の対積oracleと比較した。入れ子の上限計算は160個のランダム候補集合の全部分集合と比較した。CLIと既存NMRの回帰を含め60件のCTestが通った。

## 300配列の回帰と速度

| 条件 | 全対F1 | PK対F1 | 時間合計 | スコアなし基準比 | 最大追加連続変数／行 |
|---|---:|---:|---:|---:|---:|
| スコアなし | 0.624928 | 0.231560 | 16.900秒 | 1.00 | 0 / 0 |
| 前回のバイナリ、同じ統合スコア | 0.628189 | 0.243064 | 28.247秒 | 1.67 | 110 / 381 |
| 現在のバイナリ、従来式 | 0.628189 | 0.243064 | 28.255秒 | 1.67 | 110 / 381 |
| **現在のバイナリ、下側行削除** | **0.628189** | **0.243064** | **26.658秒** | **1.58** | **110 / 172** |

新式／従来式の時間比は0.94349、95%対応bootstrap区間 `[0.90975,0.97285]`。短縮率の点推定5.65%、区間は約2.72〜9.02%。最大追加行数は381→172（約55%削減）だったが、全体の時間短縮は約6%であり、行数の減少率に比例するものではなかった。

全300配列の予測は、元のバイナリ・現在の従来式・新式で同一。三反復の予測も一致した。PK対TP530、FP1588、FN1713、PKフリー150配列の偽PK数62は変わらない。前回の保存済み結果とも一致した。各閾値の目的値の最大差は約1e-11で、今回は許容ギャップによる実質的な差はなかった。求解回数は全条件2971、追加整数変数・BPP計算・refinementは0。

今回の診断では、スコアなしのノード数1330、LP反復数43348に対し、従来式は1362、109313。ノード数は約2%、LP反復数は約152%増加した。新式は1341、112487で、LP反復数自体は従来式より約3%多かったが、追加行を減らした状態で最適化時間は26.984→25.394秒へ短縮した。PK定式化の時間は0.103→0.102秒でほぼ同じ。モデルのLP処理を軽くする変更による短縮であり、特徴計算の高速化によるものではない。

元のバイナリと現在の従来式の時間比は1.00026、95%区間 `[0.99539,1.00506]`。新しい診断出力や実装追加だけによる速度差は、この対照では確認できなかった。今回の秒数と前回の29.294秒を直接引いて短縮率とはしない。同じ測定内の対照を使う。

二段階の調整比較各5076試行と、300配列の回帰比較3600試行の計13752試行は全て成功。20秒のタイムアウトは0。各入力BPP、実際のコマンド、ログ、予測、集計値、ソースとバイナリのハッシュ、設定選択、停止ギャップの診断を照合した。[監査済みの全結果・由来](measurements/crossing-speed-summary.json) と [配列ごとの結果](measurements/crossing-speed-per-rna.json) を保存した。

同レベルのPKフリー性による上下限の強化や数値正規化だけでは、今回の求解時間増加を解消できなかった。最大化に不要な行を削る方法は精度を保って短縮できたが、スコアによる時間増加の大半は残る。長いRNAで同じ短縮率になるかは未検証であり、線形個の補助変数だから低負荷になるとは仮定しない。

## 使用方法と再現資料

前回の統合スコアのコマンドへ `--pk-crossing-hypograph` を追加する。

```sh
./build/ipknot -r 0 -t auto,auto \
  --pk-h-formulation crossing --pk-h-allocation blocks \
  --pk-h-max-stem 200 --pk-h-max-loop 200 --pk-selection-weight 0 \
  --pk-learned-model experiments/pk-score/models/hybrid-r0-v1-posterior.txt \
  --pk-learned-scale 0.05 --pk-hybrid-shape \
  --pk-h-intercept -0.05 --pk-h-stem-reward 0.025 --pk-h-loop-penalty 0.0075 \
  --pk-h-weight 1 --pk-crossing-simplify --pk-crossing-hypograph input.fa
```

新しい定式化はオプトイン。全ての新フラグを付けなければ従来式を使う。通常の推論に実験スナップショットは不要。

比較処理は [crossing_speed.py](crossing_speed.py)、停止ギャップの検証後の選択処理は [select_crossing_speed.py](select_crossing_speed.py)、保存出力の監査は [summarize_crossing_speed.py](summarize_crossing_speed.py)。完全な実験再実行には以前のR0 BPP・manifest・frozen設定と、元のバイナリが必要。最初の比較時のソースとバイナリはローカルのsource-snapshotと `/tmp/ipknot-crossing-speed-pilot` に保存した。診断バイナリの変更ソース、コンパイル・リンク引数、入力と結果のハッシュもstrict-probe以下に保存する。

`IPKNOT_HIGHS_DIAGNOSTICS=1` は追加の探索ノード数・LP反復数を標準エラーへ出す。`IPKNOT_HIGHS_LOG=1` はHiGHSの詳細ログを有効にする。どちらも通常は未設定とし、比較測定では元のバイナリを除く全条件で同じ診断設定を使った。
